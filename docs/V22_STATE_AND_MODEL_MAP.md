# Creator OS v2.2 상태값/데이터 모델 매핑

작성일: 2026-06-30

이 문서는 Creator OS v2.2 설계도를 현재 앱에 적용하기 전에, 기존 기능을 깨지 않기 위해 만든 기준표입니다. 목적은 "무엇을 지금 맞추고, 무엇을 나중에 바꿀지"를 분리하는 것입니다.

## 결론

지금 바로 큰 DB 분리나 AI 기능을 붙이면 위험합니다. 먼저 상태값과 필드 이름을 표준화하고, 기존 데이터와 호환되는 방식으로 천천히 확장해야 합니다.

가장 중요한 결정은 다음 3가지입니다.

1. 영상 상태는 장기적으로 `statusIds` 복수 상태를 지원해야 합니다.
2. 현재 단일 `status` 값은 당장 삭제하지 말고 호환 필드로 유지해야 합니다.
3. 채널 `grade`와 `status`는 UI보다 먼저 필드 기준을 확정해야 합니다.

## 현재 코드에서 확인된 상태값

### 영상/레이더 상태

| 현재 저장값 | 현재 의미 | v2.2 기준 대응 | 판단 |
|---|---|---|---|
| `reviewed` | 레이더에서 검토 완료, 다시 숨김 | `확인함` | 유지 가능. 표시명만 `확인함`으로 통일 권장 |
| `later` | 레이더에서 나중에 보기 | `다시 보기` 또는 `보류` | 의미가 모호함. 영상 상태에서는 `watch_later`, 제작 후보에서는 `production_on_hold`로 분리 권장 |
| `production_candidate` | 제작 후보함/칸반으로 이동 | `제작 후보` 또는 제작 후보 상태 `후보` | 유지 가능. 단, 영상 상태와 제작 상태를 분리해야 함 |
| `production_active` | 제작 중 | 제작 후보 상태 `제작 중` | 유지 가능 |
| `uploaded` | 업로드 완료 | 제작 후보 상태 `완료`, 영상 상태 `사용함` | 위험. 완료 기록과 사용함을 구분해야 함 |

### 화면/메뉴 상태

| 현재 저장값 | 현재 의미 | 판단 |
|---|---|---|
| `live` | 현재 사용 가능한 메뉴 | 제품 UI 상태. v2.2 데이터 상태와 혼동 금지 |
| `soon` | 준비 중 메뉴 | 제품 UI 상태. 영상/채널 상태와 혼동 금지 |

### 수집 상태

| 현재 저장값 | 현재 의미 | v2.2 기준 대응 | 판단 |
|---|---|---|---|
| `success` | 스캔 성공 | 수집 로그 상태 | 유지 |
| `partial` | 부분 성공 | 수집 로그 상태 | 유지 |
| `failed` | 실패 | 수집 로그 상태 | 유지 |
| `none` | 수집 기록 없음 | 수집 로그 상태 | 유지 |

## v2.2 기준으로 확정할 상태값

### 채널 등급 `channel.grade`

| 저장값 | 화면 표시 | 의미 |
|---|---|---|
| `S` | S | 핵심 벤치마킹 채널 |
| `A` | A | 자주 참고할 채널 |
| `B` | B | 눈여겨볼 채널 |
| `C` | C | 보통 참고 채널 |
| `unclassified` | 미분류 | 판단 전 |

주의: 등급은 스캔 주기와 레이더 우선순위에 연결될 예정입니다. 지금은 표시/저장 기준만 먼저 맞추고, 자동 스캔 연결은 나중에 합니다.

### 채널 상태 `channel.status`

| 저장값 | 화면 표시 | 의미 |
|---|---|---|
| `active` | 활성 | 사용자가 수동 수집 대상으로 선택할 수 있음. 자동 수집 승인은 아님 |
| `paused` | 보류 | 스캔 제외, 나중에 재검토 |
| `discarded` | 폐기 | 자동 수집 완전 제외, 기본 숨김 |

주의: `grade`와 `status`는 별개입니다. S등급 채널도 보류가 될 수 있고, C등급 채널도 활성일 수 있습니다.

자동 수집 여부는 `status`가 아니라 `collectionMode`로 별도 판단합니다. 새 채널의 기본값은 `manual`이며, 야간 자동 수집은 `status: active`이면서 `collectionMode: auto`로 명시된 채널만 대상으로 합니다.

### 영상 상태 `video_user_records.statusIds`

장기 목표는 복수 상태입니다. 예를 들어 하나의 영상이 `제작 후보`이면서 `자료 참고`일 수 있어야 합니다.

| 저장값 | 화면 표시 | 의미 |
|---|---|---|
| `unseen` | 아직 안 봄 | 기본 상태 |
| `opened` | 유튜브 열어봄 | 앱에서 유튜브 링크 클릭 |
| `reviewed` | 확인함 | 앱에서 검토 완료 |
| `watch_later` | 다시 보기 | 우선 노출할 보류 영상 |
| `production_candidate` | 제작 후보 | 제작실로 보낸 영상 |
| `reference_material` | 자료 참고 | 참고 자료로 보관 |
| `title_reference` | 제목 참고 | 제목 아이디어로 보관 |
| `excluded` | 제외 | 기본 검색/레이더에서 숨김 |
| `used` | 사용함 | 실제 콘텐츠 제작에 사용 |

현재 코드의 `status` 단일값은 바로 삭제하지 않습니다. 다음 단계에서는 `status`를 읽어서 `statusIds`처럼 해석하는 호환 함수를 먼저 둡니다.

### 제작 후보 상태 `production.status`

현재 앱은 별도 `production_candidates` DB 없이 `video_user_records.status`로 제작 칸반을 표현합니다. 당장 별도 DB를 만들지 않고, 현재 구조 안에서 다음 값을 단계적으로 맞춥니다.

| v2.2 저장값 | 화면 표시 | 현재 대응 | 적용 순서 |
|---|---|---|---|
| `candidate` | 후보 | `production_candidate` | 1차 호환 |
| `reviewing` | 검토 중 | 없음 | 2차 추가 |
| `decided` | 제작 결정 | 없음 | 2차 추가 |
| `active` | 제작 중 | `production_active` | 1차 호환 |
| `done` | 완료 | `uploaded` | 1차 호환, 이름 재검토 |
| `on_hold` | 보류 | `later`와 혼동 중 | 2차 추가 |

권장: 저장값을 한 번에 바꾸지 말고, 화면과 변환 함수부터 추가합니다. 기존 `production_candidate`, `production_active`, `uploaded` 데이터가 계속 읽혀야 합니다.

## 현재 구조에서 위험한 변경

### 1. `status`를 바로 `statusIds`로 교체

위험합니다. 현재 레이더와 제작 칸반이 `record.status`를 직접 봅니다. 바로 바꾸면 레이더 숨김, 제작 후보 표시, 업로드 완료 표시가 깨질 수 있습니다.

권장 방식:

1. `getVideoStatusIds(record)` 호환 함수 추가
2. 기존 `status`와 신규 `statusIds`를 함께 읽기
3. 저장 시 당분간 둘 다 기록
4. 충분히 안정화된 뒤 단일 `status` 의존 제거

### 2. `production_candidates` 별도 DB 즉시 도입

위험합니다. 별도 DB는 장기적으로 맞지만, 지금 도입하면 프론트, 백엔드, 기존 저장 데이터 이전이 한 번에 필요합니다.

권장 방식:

1. 현재 `video_user_records` 기반 제작 칸반 유지
2. 제작 상태와 메모 필드 이름을 v2.2에 맞게 정리
3. 실제 제작 후보가 여러 원본 영상을 묶어야 할 때 별도 DB 도입

### 3. AI 자동 태깅을 수집 시 바로 실행

위험합니다. 비용, 실패 처리, 재시도, 설정창, API Key 관리가 먼저 필요합니다.

권장 방식:

1. 규칙 기반 제목 패턴 태그부터 검토
2. AI는 on-demand 버튼으로 시작
3. 비용 표시와 설정이 생긴 뒤 자동 실행 검토

### 4. 자동 스캔 스케줄링 즉시 도입

위험합니다. YouTube API 비용과 할당량 관리가 직접 연결됩니다.

권장 방식:

1. 채널 grade/status 필드 먼저 확정
2. 수동 스캔에서 등급/상태 기준을 참고
3. API 사용량 대시보드 이후 자동화 검토

## 작업 우선순위

### Phase A. 기준 정리

목표: 기존 기능을 깨지 않고 v2.2 기준과 현재 코드를 연결합니다.

1. 이 문서를 기준으로 상태값 이름 확정
2. 상태값 상수 파일 추가
3. `status` 호환 함수 추가
4. 레이더와 제작 칸반이 호환 함수를 사용하게 변경

완료 기준:

- 기존 `reviewed`, `later`, `production_candidate`, `production_active`, `uploaded`가 그대로 동작합니다.
- 새 구조인 `statusIds`를 일부 기록해도 화면이 깨지지 않습니다.

### Phase B. 채널 기준 도입

목표: 채널의 중요도와 수집 대상 여부를 분리합니다.

1. `channel.grade` 기본값 `unclassified`
2. `channel.status` 기본값 `active`
3. 채널 목록에 등급/상태 표시
4. 레이더 정렬에서 등급을 참고하되, API 호출은 추가하지 않음

완료 기준:

- 채널이 S/A/B/C/미분류로 보입니다.
- 보류/폐기 채널은 새 추천에서 제외할 준비가 됩니다.

### Phase C. 제작 칸반 상태 확장

목표: 제작 흐름을 v2.2 기준에 가깝게 만듭니다.

1. 기존 3단계 유지: 제작 후보, 제작 중, 업로드 완료
2. 보류 단계 추가
3. 검토 중/제작 결정 단계 추가
4. `uploaded`와 `used` 의미 분리

완료 기준:

- 제작 후보가 "볼 것"과 "만들 것"으로 더 잘 분리됩니다.
- 업로드 완료가 곧바로 모든 곳에서 숨김 처리되는 위험이 줄어듭니다.

### Phase D. 기능 확장

목표: v2.2의 큰 기능을 안전하게 추가합니다.

1. 영상 카드/슬라이드 패널
2. 인사이트 검색
3. 설정창 최소 버전
4. AI on-demand 기능
5. 자동 스캔/할당량 대시보드
