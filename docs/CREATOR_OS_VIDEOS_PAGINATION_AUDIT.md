# Creator OS 저장 영상 조회 페이지네이션 감사

작성일: 2026-07-02

이 문서는 `GET /videos?channelIds=...` 저장 영상 조회에 페이지네이션이 지금 필요한지 평가하기 위한 감사 문서입니다.

중요: 이 문서는 분석 문서입니다. 코드, API, DB schema, localStorage key는 변경하지 않습니다.

---

## 1. 현재 기준 사실

현재 프론트 구현:

- 저장 영상 불러오기는 `fetchStoredVideosByChannelIds(channelIds)`를 사용합니다.
- 실제 호출은 `GET /videos?channelIds=${channelIds.join(',')}`입니다.
- 이 작업은 Cloud DB 조회입니다.
- YouTube API를 새로 호출하지 않습니다.
- 응답은 `data.videos || []` 배열 전체를 한 번에 받습니다.
- 프론트는 받은 전체 배열을 `mapStoredVideosToViewModels()`로 변환한 뒤 `videos` state에 저장합니다.
- 검색, 조회수 필터, 길이 필터, 정렬, 카드/리스트 보기는 현재 프론트 메모리 안의 전체 `videos` 배열 기준으로 동작합니다.

현재 문서 기준:

- `GET /videos?channelIds=...`는 저장된 영상 데이터를 읽는 DB 조회입니다.
- 기존 무페이지 요청은 전체 조회 구조를 유지합니다.
- 2026-07-26부터 선택형 `pageSize`/`continuationToken` 조회도 지원합니다.
- 프론트는 모든 페이지를 합친 전체 배열을 기준으로 검색, 필터, 정렬합니다.

## 2. 2026-07-02 운영 데이터 측정

배포된 Function API에서 Cloud DB 조회만 실행해 확인했습니다.

실행한 조회:

- `GET /channels`
- `GET /videos?channelIds=...`

주의:

- YouTube API 호출은 하지 않았습니다.
- 새 영상 수집은 하지 않았습니다.
- DB 변경은 하지 않았습니다.

확인 결과:

| 항목 | 값 |
|---|---:|
| 저장 채널 수 | 10개 |
| 활성 채널 수 | 10개 |
| 저장 영상 수 | 1,821개 |
| `/videos` 응답 크기 | 약 1.16MB |
| 응답 성공 여부 | 성공 |

현재 판정:

- 지금 데이터 규모에서는 즉시 페이지네이션을 도입해야 할 정도는 아닙니다.
- 다만 채널 수와 영상 수가 늘면 앱 첫 조회와 필터/정렬 체감 속도에 영향을 줄 수 있습니다.

## 3. 현재 프론트 흐름

```txt
사용자가 채널 선택
→ 저장 영상 불러오기 클릭
→ GET /videos?channelIds=...
→ 전체 videos 배열 수신
→ mapStoredVideosToViewModels()
→ videos state에 전체 저장
→ 프론트에서 검색/필터/정렬/터또터 모드 처리
→ 카드/리스트 전체 렌더링
```

장점:

- 구조가 단순합니다.
- 필터와 정렬이 전체 데이터 기준으로 일관됩니다.
- 터또터 후보와 대박지수 정렬도 전체 결과를 보고 계산할 수 있습니다.

단점:

- 영상 수가 커지면 첫 로딩이 무거워집니다.
- 모든 영상을 메모리에 올립니다.
- 카드 보기에서 렌더링 부담이 커질 수 있습니다.
- 백엔드에서 한 번에 읽는 데이터가 많아질 수 있습니다.

---

## 4. 페이지네이션을 바로 넣으면 생기는 문제

페이지네이션은 단순히 `limit=50`을 붙이는 문제가 아닙니다.

현재 화면은 전체 영상 배열을 기준으로 아래 기능을 수행합니다.

- 제목 검색
- 조회수 필터
- 쇼츠/롱폼 필터
- 최신순 정렬
- 대박지수 정렬
- 일평균 화제성 정렬
- 참여율 정렬
- 터또터 후보 필터
- 스크랩/제작 후보 표시

서버 페이지네이션을 바로 적용하면 아래 문제가 생길 수 있습니다.

| 문제 | 설명 |
|---|---|
| 전체 정렬 깨짐 | 1페이지 안에서만 대박지수순이 되면 전체 1등 후보가 뒤 페이지에 남을 수 있음 |
| 필터 결과 오해 | 1페이지에 없다는 이유로 "결과 없음"처럼 보일 수 있음 |
| 터또터 후보 누락 | 오래된 영상이 뒤 페이지에 있으면 레이더가 후보를 못 볼 수 있음 |
| 스크랩/제작 후보 카운트 차이 | 일부 페이지만 로드하면 전체 카운트와 화면 카운트가 달라질 수 있음 |
| UX 복잡도 증가 | "더 불러오기", "전체 검색", "현재 페이지 검색" 구분이 필요 |

따라서 페이지네이션을 구현한다면 프론트 필터/정렬 정책도 같이 결정해야 합니다.

## 5. 선택지

### 선택지 A: 지금은 전체 조회 유지

설명:

- 현재 구조를 유지합니다.
- 데이터가 더 커질 때까지 페이지네이션을 미룹니다.

장점:

- 가장 안전합니다.
- 필터/정렬/터또터 흐름을 깨지 않습니다.
- API 응답 구조 변경이 없습니다.

단점:

- 데이터가 커지면 나중에 성능 문제가 생길 수 있습니다.
- 응답 크기와 렌더링 비용이 계속 증가합니다.

적합한 경우:

- 현재처럼 영상 수가 1,000~3,000개 수준일 때
- 실사용 속도가 아직 괜찮을 때
- 1차 완성 전에 큰 API 변경을 피하고 싶을 때

### 선택지 B: 프론트 렌더링만 가볍게 만들기

설명:

- API는 전체 조회를 유지합니다.
- 화면 렌더링만 일부 제한합니다.
- 예: 첫 화면은 상위 N개만 렌더링, 더보기 버튼, 리스트 가상화 검토

장점:

- API 변경 없이 체감 속도를 개선할 수 있습니다.
- 전체 데이터 기준 필터/정렬은 유지됩니다.
- 백엔드 변경이 없습니다.

단점:

- 응답 크기 문제는 해결하지 못합니다.
- 영상 수가 매우 커지면 근본 해결은 아닙니다.
- 가상화 라이브러리를 도입하면 새 라이브러리 결정이 필요할 수 있습니다.

적합한 경우:

- 로딩보다 화면 스크롤/렌더링이 느릴 때
- API 응답 크기는 아직 괜찮지만 카드가 많아 UI가 무거울 때

### 선택지 C: 백엔드 cursor pagination 추가

설명:

`GET /videos`에 선택 파라미터를 추가합니다.

예상 형태:

```txt
GET /videos?channelIds=...&limit=100&continuationToken=...
```

예상 응답:

```txt
{
  success: true,
  videos: [...],
  nextContinuationToken: "...",
  totalApprox: 1234
}
```

장점:

- 응답 크기를 줄일 수 있습니다.
- 영상 수가 많아져도 첫 로딩을 가볍게 만들 수 있습니다.
- 장기적으로 가장 일반적인 방향입니다.

단점:

- 백엔드 endpoint 변경이 필요합니다.
- 프론트 로딩 로직 변경이 필요합니다.
- 전체 정렬/필터/터또터 기준을 서버와 맞춰야 합니다.
- Cosmos continuation token, 정렬 기준, channelIds 필터를 함께 설계해야 합니다.

적합한 경우:

- 저장 영상이 5,000개 이상으로 늘어날 때
- `/videos` 응답이 5MB 이상으로 커질 때
- 저장 영상 불러오기가 3초 이상 걸릴 때

### 선택지 D: 서버 검색/정렬 API로 확장

설명:

페이지네이션뿐 아니라 서버가 검색, 필터, 정렬을 함께 처리합니다.

예상 형태:

```txt
GET /videos?channelIds=...&sort=multiplier&length=shorts&minViews=100000&query=...
```

장점:

- 장기적으로 가장 정확합니다.
- 전체 데이터 기준 정렬/필터가 유지됩니다.
- 프론트 메모리 부담을 줄일 수 있습니다.

단점:

- 백엔드 설계 범위가 큽니다.
- 인덱스와 쿼리 비용 검토가 필요합니다.
- 기존 프론트 필터/정렬 로직을 많이 바꿔야 합니다.

적합한 경우:

- 영상 데이터가 크게 늘고, 검색/정렬 품질이 핵심 기능이 될 때
- 사용자별 저장 상태와 영상 조건을 함께 조합해야 할 때

## 6. Codex 추천

현재는 **선택지 A: 전체 조회 유지**를 추천합니다.

이유:

1. 현재 측정값은 저장 영상 1,821개, 응답 약 1.16MB입니다.
2. 지금 당장 페이지네이션을 넣으면 대박지수/터또터/검색/정렬의 전체 기준이 흔들릴 수 있습니다.
3. 1차 완성 전에는 API 응답 구조 변경보다 Creator OS 흐름 안정화가 더 중요합니다.
4. 현재 병목이 확인된 상태가 아니라 예방적 대수술에 가깝습니다.

단, 아래 조건 중 하나가 발생하면 다시 검토합니다.

- 저장 영상 5,000개 이상
- `/videos` 응답 5MB 이상
- 저장 영상 불러오기 3초 이상
- 카드/리스트 스크롤이 눈에 띄게 끊김
- 모바일 화면에서 렌더링 지연이 커짐

## 9. 최종 판정

2026-07-26 사용자 승인으로 선택지 B를 적용했습니다.

- 백엔드는 `pageSize`와 `continuationToken`을 선택 파라미터로 지원합니다.
- 파라미터가 없는 기존 호출과 응답 구조는 그대로 유지합니다.
- 프론트는 기본 200개씩 모든 페이지를 순차 조회하고, 완료된 전체 목록만 화면에 반영합니다.
- 중간 페이지 실패 시 부분 목록을 성공 결과처럼 노출하지 않습니다.
- 서버 검색/정렬과 새 라이브러리는 도입하지 않았습니다.
- 이 흐름은 Cloud DB 조회이며 YouTube API 호출량을 늘리지 않습니다.

따라서 대박지수/터또터/검색/정렬은 계속 선택 채널의 전체 저장 영상 기준으로 동작합니다. 다음 성능 확장은 실사용 로딩 시간과 데이터 규모를 측정한 뒤 별도 판단합니다.
