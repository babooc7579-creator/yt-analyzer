# Creator OS 카테고리 / 채널 태그 저장 구조 감사

작성일: 2026-07-02

이 문서는 Creator OS의 카테고리 목록과 Cloud 채널 태그가 어떻게 연결되어 있는지 정리합니다.

중요: 이 문서는 분석 문서입니다. 코드, API, DB schema, localStorage key는 변경하지 않습니다.

---

## 1. 현재 기준 사실

아래 내용은 2026-07-02 기준 repo 확인 결과입니다.

- 화면의 카테고리 목록은 localStorage `yt_crm_categories`에 저장됩니다.
- 기본 카테고리는 `DEFAULT_CATEGORIES` 상수에서 시작합니다.
- 실제 채널 문서에는 `tags` 배열과 `category` 필드가 Cloud DB에 저장됩니다.
- 채널 생성 시 선택한 첫 번째 태그가 `category`가 됩니다.
- 백엔드 주석 기준 `category`는 Cosmos partition key로 쓰이는 내부용 값입니다.
- 카테고리 추가/삭제는 현재 프론트 localStorage 목록만 바꿉니다.
- 카테고리 이름 변경은 `/tags/rename`을 호출해 Cloud 채널의 `tags`와 `category`를 함께 바꿉니다.
- `GET /tags/rename`은 메서드는 GET이지만 실제로 DB를 변경합니다.
- 태그별 스캔은 채널의 `tags` 배열에 해당 카테고리가 포함된 채널만 대상으로 합니다.
- 채널 삭제/수정/기록 추가는 `category` query param을 사용해 Cloud 문서를 찾습니다.

## 2. 현재 저장 위치

| 데이터 | 현재 저장 위치 | 기준 데이터 여부 | 설명 |
|---|---|---|---|
| 화면 카테고리 목록 | localStorage `yt_crm_categories` | UI 기준 | 탭, 태그 선택 버튼을 그리는 목록 |
| 기본 카테고리 | `src/constants/categories.js` | 초기값 | localStorage가 없을 때 사용 |
| 채널 태그 | Cloud DB `channels.tags` | 실제 채널 기준 | 채널이 어떤 결에 속하는지 |
| 채널 대표 카테고리 | Cloud DB `channels.category` | 내부 기준 | 첫 번째 태그, Cosmos partition key로 사용 |

## 3. 현재 사용자 흐름

### 3.1 카테고리 추가

```txt
카테고리 설정
→ 새 카테고리명 입력
→ + 버튼 클릭
→ categories state 변경
→ localStorage 저장
```

현재 영향:

- 화면의 카테고리 목록에 새 항목이 생깁니다.
- Cloud 채널 데이터는 바뀌지 않습니다.
- 새 채널 저장 시 이 카테고리를 태그로 선택할 수 있습니다.

위험:

- 아직 해당 태그가 붙은 채널이 없으면 빈 카테고리로 보입니다.

### 3.2 카테고리 삭제

```txt
카테고리 설정
→ 휴지통 클릭
→ categories state에서 제거
→ localStorage 저장
```

현재 영향:

- 화면의 카테고리 목록에서만 사라집니다.
- Cloud 채널의 `tags`와 `category`는 바뀌지 않습니다.
- 해당 태그가 붙은 채널은 Cloud에 그대로 남습니다.

위험:

- 사용자는 태그가 삭제됐다고 생각할 수 있지만 실제 채널 태그는 남아 있습니다.
- Cloud에는 태그가 있는데 화면 탭에는 보이지 않는 상태가 생길 수 있습니다.

### 3.3 카테고리 이름 변경

```txt
카테고리 설정
→ 톱니바퀴 클릭
→ 새 이름 입력
→ /tags/rename 호출
→ Cloud 채널 tags/category 변경
→ local categories 목록도 변경
```

현재 영향:

- localStorage 카테고리 목록이 바뀝니다.
- Cloud 채널의 `tags` 배열이 바뀝니다.
- Cloud 채널의 `category`가 기존 이름과 같으면 같이 바뀝니다.

위험:

- `GET /tags/rename`은 실제 DB 변경 작업입니다.
- `category`가 Cosmos partition key라면, 이름 변경은 단순 표시명 변경보다 민감할 수 있습니다.
- 백엔드는 `upsert`로 변경된 문서를 저장하지만, partition key 변경 시 기존 partition 문서 처리 방식은 별도 검증이 필요합니다.

### 3.4 태그별 새 영상 수집

```txt
카테고리 탭의 새 영상 수집 클릭
→ /scan?tag=카테고리 호출
→ 백엔드가 channels.tags에 해당 태그가 있는 채널만 스캔
```

현재 영향:

- 화면의 local categories 목록이 스캔 버튼을 만듭니다.
- 실제 스캔 대상은 Cloud 채널의 `tags` 기준입니다.

위험:

- local categories에 없는 Cloud 태그는 탭에 보이지 않아 스캔하기 어렵습니다.
- local categories에는 있지만 Cloud 채널에 없는 태그는 빈 탭이 됩니다.

## 4. 현재 불일치 가능성

| 불일치 | 예시 | 사용자 영향 | 위험도 |
|---|---|---|---:|
| local에는 있는데 Cloud에는 없음 | 새 카테고리만 만들고 채널 없음 | 빈 탭 표시 | 낮음 |
| Cloud에는 있는데 local에는 없음 | local에서 카테고리 삭제, Cloud 태그는 남음 | 채널이 화면에서 찾기 어려워짐 | 높음 |
| `tags`에는 있는데 `category`가 다름 | 여러 태그 중 첫 번째 태그가 변경됨 | 삭제/수정 API의 category param 혼동 | 중간 |
| 카테고리 이름 변경이 partition key 변경과 연결 | `해짜` → `해외짜집기` | 중복 문서 또는 기존 문서 접근 문제 가능 | 높음 |
| local categories가 여러 브라우저에서 다름 | PC A와 PC B의 탭 목록 다름 | 같은 Cloud 채널인데 화면 구성이 다름 | 중간 |

## 5. 선택지 A: 현재 구조 유지

### 설명

카테고리 목록은 localStorage에 두고, Cloud 채널 태그는 지금처럼 별도로 유지합니다.

### 장점

- 구현 변경이 없습니다.
- 기존 화면이 그대로 동작합니다.
- 빠릅니다.

### 단점

- local 카테고리와 Cloud 태그가 계속 어긋날 수 있습니다.
- 카테고리 삭제가 실제 태그 삭제인지 UI 숨김인지 헷갈립니다.
- 여러 기기에서 카테고리 목록이 달라질 수 있습니다.

### 적합한 경우

- 당장 기능 안정화가 우선일 때
- 카테고리 목록이 개인 화면 설정에 가깝다고 볼 때

---

## 6. 선택지 B: Cloud 채널 태그에서 카테고리 목록을 파생

### 설명

화면 카테고리 목록을 localStorage 기준이 아니라 Cloud 채널의 `tags`를 모아서 만듭니다.

예상 흐름:

```txt
GET /channels
→ 모든 channel.tags 수집
→ 카테고리 탭 생성
```

### 장점

- Cloud와 화면이 더 잘 맞습니다.
- Cloud에 있는 태그가 화면에서 사라지는 위험이 줄어듭니다.
- 여러 브라우저에서 같은 카테고리 목록을 볼 수 있습니다.

### 단점

- 채널이 하나도 없는 새 카테고리를 미리 만들기 어렵습니다.
- 카테고리 순서, 숨김, 즐겨찾기 같은 UI 설정은 별도 저장소가 필요할 수 있습니다.
- 기존 `yt_crm_categories`와의 관계를 정해야 합니다.

### 적합한 경우

- 카테고리를 실제 Cloud 태그의 목록으로 보고 싶을 때
- 여러 기기/브라우저에서 같은 화면 기준이 필요할 때

---

## 7. 선택지 C: Cloud 태그 + local UI 설정 분리

### 설명

Cloud 채널 태그를 실제 기준으로 삼고, localStorage는 화면 표시 설정만 담당합니다.

예상 구조:

```txt
Cloud tags: 실제 존재하는 태그 목록
local categories: 정렬 순서, 숨김 여부, 자주 쓰는 태그
```

### 장점

- 실제 데이터 기준과 화면 취향을 분리할 수 있습니다.
- Cloud에 있는 태그가 사라지는 위험을 줄입니다.
- 사용자는 카테고리 순서나 숨김을 개인화할 수 있습니다.

### 단점

- 구현이 더 복잡합니다.
- "삭제"가 실제 태그 삭제인지 화면에서 숨김인지 UI 문구를 명확히 해야 합니다.
- localStorage key의 의미를 바꾸면 마이그레이션 판단이 필요합니다.

### 적합한 경우

- 태그는 Cloud 기준으로 안정화하고 싶지만, 화면 순서/숨김은 개인화하고 싶을 때

---

## 8. 선택지 D: 카테고리 관리 API 신설

### 설명

카테고리를 별도 Cloud 데이터로 관리합니다.

예상 구조:

```txt
categories container 또는 settings document
→ id, label, order, hidden, color 등 저장
```

### 장점

- 카테고리 관리가 가장 명확해집니다.
- 여러 기기에서 동일한 카테고리 UI를 사용할 수 있습니다.
- 정렬, 색상, 설명, 보관 여부 등 확장이 쉽습니다.

### 단점

- 새 endpoint 또는 DB schema가 필요합니다.
- 현재 단계에서는 범위가 큽니다.
- 채널 태그와 카테고리 설정 간 동기화 정책이 필요합니다.

### 적합한 경우

- Creator OS가 개인용을 넘어 여러 사용자/기기에서 일관된 설정이 필요해질 때

## 9. Codex 추천

현재 단계에서는 **선택지 C: Cloud 태그 + local UI 설정 분리**를 장기 방향으로 추천합니다.

단, 바로 구현하지는 않습니다.

단기적으로는 다음이 안전합니다.

1. 카테고리 삭제는 실제 Cloud 태그 삭제가 아니라 "화면 목록에서 제거"임을 명확히 표시합니다.
2. Cloud 채널에 있는데 local categories에 없는 태그를 감지하는 audit 또는 안내를 추가합니다.
3. 카테고리 이름 변경은 DB 변경 작업이므로 더 강한 확인 UI가 필요합니다.
4. `category`가 partition key로 쓰이는 구조이므로 이름 변경 로직은 백엔드에서 더 신중히 검토해야 합니다.

2026-07-15에는 이 단기 원칙을 설명하고 기존 카테고리 관리 기능을 모아 보여주는 독립 `설정` 화면을 연결했습니다. 저장 구조, localStorage key, `/tags/rename` 동작과 장기 선택지 C의 데이터 모델은 변경하지 않았습니다.

## 10. 지금 결정하지 말아야 할 것

이 문서에서는 아래 항목을 결정하지 않습니다.

- localStorage `yt_crm_categories` 제거 여부
- 카테고리 Cloud 저장소 추가 여부
- `/tags/rename` endpoint 변경 여부
- 카테고리 삭제 시 Cloud 채널 태그까지 삭제할지 여부
- `category` partition key 구조 변경 여부
- 카테고리 정렬/숨김 설정 schema

이 항목은 기존 채널 데이터와 API 동작에 영향을 줄 수 있으므로 별도 선택지 보고 후 결정합니다.

## 12. 최종 판정

현재 카테고리 구조는 MVP로는 동작하지만, 데이터 기준으로는 불안정합니다.

현재 판정:

- 카테고리 탭 표시: 가능
- 채널 태그 저장: 가능
- 태그별 스캔: 가능
- 카테고리 추가: local UI 추가로 가능
- 카테고리 삭제: Cloud 태그 삭제가 아니므로 오해 위험
- 카테고리 이름 변경: Cloud DB 변경이므로 고위험

따라서 지금은 구조 변경보다 먼저 "카테고리"와 "Cloud 채널 태그"의 의미를 화면과 문서에서 분리하는 것이 안전합니다.
