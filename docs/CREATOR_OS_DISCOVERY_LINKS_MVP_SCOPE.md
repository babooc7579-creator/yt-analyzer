# Creator OS discovery links / local assets MVP 범위 선택지

작성일: 2026-07-02

이 문서는 Creator OS에서 인스타/외부 링크와 로컬 파일 연결을 1차 MVP에서 어디까지 다룰지 정리합니다.

중요: 이 문서는 범위 결정 문서입니다. 코드, API, DB schema, localStorage key는 변경하지 않습니다.

---

## 1. 현재 기준 사실

아래 내용은 2026-07-03 현재 repo 기준입니다. 이후 1차 MVP로 수동 링크 저장 발견함이 부분 구현되었습니다.

- `discovery_links` 별도 Cosmos container는 없습니다.
- `/discovery-links` API는 존재하며, 기존 `videos` container 안의 `docType: discovery_link` 문서로 저장합니다.
- `local_assets` 저장소는 없습니다.
- discovery links 관련 API는 1차 MVP 범위로 구현되었습니다.
- local assets 관련 API는 없습니다.
- 인스타/외부 링크 수동 저장 기능은 1차 MVP 범위로 부분 구현되어 있습니다.
- 새 discovery link 저장 시 URL 기준 `platform` 추정값을 Cloud에 저장합니다.
- 백엔드는 허용된 `platform` 값을 보존하고, 누락되거나 잘못된 값은 URL 기준으로 재추정합니다.
- 2026-07-03 사용자 결정 기준으로 원본 파일 자동 다운로드/업로드는 MVP에서 제외하고, URL 보존과 복사 편의를 우선합니다.
- 저장 영상/채널/발견 링크의 원본 URL 복사는 브라우저 클립보드 편의 기능이며, YouTube API 호출이나 DB 구조 변경을 만들지 않습니다.
- 발견 링크는 `status: candidate`로 저장해 제작 후보함에서 링크 후보로 볼 수 있습니다. 단, 별도 `production_candidates` 저장소는 만들지 않습니다.
- 로컬 파일과 원본 링크를 연결하는 기능은 아직 구현되어 있지 않습니다.
- 현재 스크랩북은 YouTube 영상 중심이며, Cloud DB `videos` container 안의 `docType: scrapbook`으로 저장됩니다.
- 현재 제작 후보는 별도 `production_candidates` 저장소 없이 `videoUserRecords` 상태값 위에서 표현됩니다.
- `CREATOR_OS_DISCOVERY_LINKS_LOCAL_ASSETS_MODEL.md`는 목표 모델 문서이며, 현재 구현 완료 목록이 아닙니다.

현재 앱에서 할 수 있는 일:

- 저장된 YouTube 영상 조회
- YouTube 영상 스크랩북 저장
- YouTube 영상별 사용자 판단 기록 저장
- 제작 후보 상태 표시
- 인스타/유튜브/틱톡/웹 링크 수동 저장
- 발견 링크 제목, 메모, 작업 상태, 권리 상태 관리
- 발견 링크 플랫폼 표시. 새 링크는 Cloud에 `platform` 저장, 기존 링크는 URL 기준 표시 fallback
- 저장 영상, 채널, 발견 링크의 원본 URL 복사
- 발견 링크를 제작 후보 상태로 보내고 제작 후보함에서 링크 후보로 확인

현재 앱에서 할 수 없는 일:

- 채널/영상/인스타 원본 파일 자동 다운로드
- 로컬 파일 자동 업로드
- 다운로드 파일과 원본 링크 연결
- 로컬 파일 출처 상태 관리
- 링크 메타데이터, 썸네일, 본문 자동 수집

## 2. 왜 범위를 작게 잡아야 하는가

discovery links / local assets는 Creator OS에서 중요한 영역입니다. 하지만 처음부터 크게 만들면 위험합니다.

주요 위험:

- 인스타 자동 수집은 크롤링/권리/약관 이슈가 있습니다.
- 로컬 파일은 브라우저 앱이 안정적으로 소유하기 어렵습니다.
- 로컬 파일 경로는 기기마다 다르고, 파일 이동/삭제에 약합니다.
- 현재 스크랩북은 YouTube 영상 중심이라 외부 링크를 섞으면 의미가 흐려질 수 있습니다.
- 제작 후보와 연결하려면 `production_candidates` 데이터 기준도 함께 흔들릴 수 있습니다.
- 새 API와 새 DB 저장소가 필요할 가능성이 높습니다.

따라서 1차 MVP는 "자동 수집"이 아니라 **사용자가 직접 붙여넣은 링크를 잃어버리지 않는 것**부터 시작하는 것이 안전합니다.

## 3. MVP 목표

1차 MVP의 목표는 다음입니다.

- 사용자가 외부에서 발견한 링크를 수동으로 저장합니다.
- 링크별로 메모와 상태를 남깁니다.
- 원본 후보, 리포스트 의심, 권리 확인 필요 같은 판단을 표시합니다.
- YouTube 저장 영상, 스크랩북, 제작 후보와 바로 섞지 않고 "발견함" 영역에 둡니다.
- 인스타/외부 사이트를 자동 크롤링하지 않습니다.
- 원본 파일을 자동 다운로드/업로드하기보다 URL을 잘 보존하고 쉽게 복사하는 흐름을 우선합니다.
- 로컬 파일 본문을 업로드하거나 브라우저가 파일 경로를 기준 데이터로 삼지 않습니다.

MVP가 해결해야 하는 사용자 문제:

- "어디서 본 소재였지?"를 잊지 않게 합니다.
- "이 링크가 원본인지 리포스트인지"를 나중에 판단할 수 있게 합니다.
- "제작에 써도 되는지 확인이 필요한 링크"를 따로 보이게 합니다.

MVP가 아직 해결하지 않는 문제:

- 채널/영상/인스타 원본 파일 자동 다운로드
- 로컬 파일 자동 업로드
- 인스타 메타데이터 자동 수집
- 로컬 파일 미리보기/재생
- 권리 확인 자동화
- 제작 칸반과 완전 연결
- AI 요약/후킹 생성

## 4. 선택지

### 선택지 A: 수동 링크 저장만 먼저 구현

내용:

- 사용자가 URL을 직접 붙여넣습니다.
- 제목과 메모는 사용자가 직접 적습니다.
- 플랫폼은 URL 문자열 기준으로 가볍게 추정할 수 있습니다.
- 상태는 사용자가 직접 바꿉니다.
- 로컬 파일은 아직 다루지 않습니다.

최소 필드 후보:

```txt
discovery_link = {
  id,
  url,
  platform,
  title,
  memo,
  status,
  rightsStatus,
  createdAt,
  updatedAt
}
```

장점:

- 가장 안전합니다.
- 인스타 크롤링, 자동 다운로드, 파일 권한 문제를 피합니다.
- 사용자가 당장 소재 링크를 잃어버리지 않게 됩니다.
- Creator OS의 "발견함" 시작점으로 충분합니다.

단점:

- 파일과 연결되지는 않습니다.
- 자동 썸네일/제목 수집이 없습니다.
- 제작 후보와의 연결은 별도 단계가 필요합니다.

위험도:

- 낮음에서 중간.

사용자 판단 필요:

- 현재 1차 MVP 구현에는 추가 판단이 필요 없습니다. 후속으로 local assets, 별도 제작 프로젝트 모델, 별도 container 분리를 할 때는 별도 판단이 필요합니다.

### 선택지 B: 수동 링크 + 파일 메모 카드

내용:

- 선택지 A에 더해, 사용자가 "내 컴퓨터에 파일 있음" 정도의 메모를 남깁니다.
- 실제 파일 업로드나 경로 저장은 하지 않습니다.
- 파일명, 폴더 힌트, 설명만 기록합니다.

최소 필드 후보:

```txt
local_asset_note = {
  id,
  displayName,
  fileHint,
  memo,
  sourceUrl,
  discoveryLinkId,
  sourceStatus,
  rightsStatus,
  createdAt,
  updatedAt
}
```

장점:

- 파일을 잃어버릴 위험을 줄입니다.
- 브라우저 파일 권한 문제를 피합니다.
- "파일은 있는데 출처가 뭐였지?" 문제를 일부 해결합니다.

단점:

- 실제 파일을 열거나 확인할 수 없습니다.
- 파일 위치가 바뀌면 사용자가 직접 수정해야 합니다.
- 링크 저장보다 입력 부담이 큽니다.

위험도:

- 중간.

사용자 판단 필요:

- 1차 MVP에 포함할지 결정 필요.

### 선택지 C: 로컬 파일 참조까지 포함

내용:

- 사용자가 파일을 선택하고 앱이 파일명/타입/참조 정보를 저장합니다.
- 가능하다면 브라우저 File API 또는 File System Access API를 검토합니다.

장점:

- 실제 파일과 소재 흐름이 더 가까워집니다.
- 제작 준비 도구에 가까워집니다.

단점:

- 브라우저 호환성과 권한 문제가 큽니다.
- 로컬 경로를 기준 데이터로 삼기 어렵습니다.
- 파일 이동/삭제 시 쉽게 깨집니다.
- 보안/개인정보 검토가 필요합니다.

위험도:

- 높음.

현재 판단:

- 1차 MVP에는 넣지 않는 것을 권장합니다.

### 선택지 D: 기존 스크랩북에 링크 타입 추가

내용:

- 별도 `discovery_links` 모델을 만들지 않고 스크랩북에 링크 타입을 추가합니다.

장점:

- 화면을 빠르게 만들 수 있습니다.
- "보관함"이라는 사용자 개념과 가까워 보일 수 있습니다.

단점:

- 현재 스크랩북은 YouTube 영상 중심입니다.
- 출처 검토 전 단계와 보관 완료 단계를 섞게 됩니다.
- 나중에 제작 후보/권리 확인/로컬 파일 연결을 붙이기 어렵습니다.
- 기존 scrapbook 구조와 의미가 흐려질 수 있습니다.

위험도:

- 중간에서 높음.

현재 판단:

- 빠르지만 장기 구조에는 불리합니다.

## 6. Codex 추천

1차 MVP는 **선택지 A: 수동 링크 저장만 먼저 구현**을 추천합니다.

추천 이유:

1. 현재 사용자의 핵심 문제는 "소재 링크를 잃어버리는 것"입니다.
2. 수동 링크 저장만으로도 인스타/외부 링크를 Creator OS 안에 넣는 첫 단계가 됩니다.
3. 자동 수집, 파일 권한, 권리 검토 같은 위험을 피할 수 있습니다.
4. 스크랩북과 제작 후보를 섞지 않고 "발견함"이라는 앞단을 만들 수 있습니다.
5. 나중에 선택지 B로 확장해 파일 메모 카드를 붙이기 쉽습니다.

추천 MVP 범위:

- URL 수동 입력
- 제목 수동 입력
- 메모 수동 입력
- 플랫폼 URL 기준 자동 추정 및 표시
- 검토 상태
- 권리 확인 상태
- 원본/리포스트 의심은 메모 또는 후속 `sourceStatus` 검토
- 링크 열기
- 링크 삭제 또는 제외
- 간단한 필터

MVP에서 제외:

- 인스타 자동 크롤링
- 메타데이터 자동 수집
- 썸네일 자동 수집
- 파일 업로드
- 로컬 파일 경로 기준 저장
- 자동 다운로드
- 제작 후보 자동 생성
- AI 자동 분석

## 7. 상태값 최소 후보

1차 MVP에서는 상태값을 너무 많이 늘리지 않습니다.

### 7.1 검토 상태

| 저장값 | 화면 표시 | 의미 |
|---|---|---|
| `inbox` | 받은 링크 | 새로 저장했고 아직 검토하지 않은 링크 |
| `reviewing` | 확인 중 | 소재성/출처 확인 중 |
| `saved` | 보관 | 나중에 다시 볼 링크 |
| `candidate` | 제작 후보 | 제작 후보로 검토할 수 있는 링크 |
| `discarded` | 제외 | 더 이상 보지 않음 |

### 7.2 출처 상태 후보

MVP에서는 원본 후보/리포스트 의심을 메인 `status`에 섞지 않습니다. 필요하면 메모로 남기고, 후속 작업에서 `sourceStatus` 별도 필드를 검토합니다.

| 저장값 후보 | 화면 표시 | 의미 |
|---|---|---|
| `unknown` | 출처 미확인 | 원본 여부 미확인 |
| `source_candidate` | 원본 후보 | 원본일 가능성 있음 |
| `repost_suspected` | 리포스트 의심 | 원본이 아닐 수 있음 |

### 7.3 권리 상태

| 저장값 | 화면 표시 | 의미 |
|---|---|---|
| `unknown` | 권리 미확인 | 아직 확인하지 않음 |
| `needs_check` | 확인 필요 | 제작 사용 전 확인 필요 |
| `cleared` | 확인 완료 | 사용자가 확인 완료로 표시함 |
| `do_not_use` | 사용 금지 | 제작에 쓰면 안 되는 자료로 판단함 |

주의:

- `status`와 `rightsStatus`는 1차 MVP 구현 기준입니다.
- `sourceStatus`는 아직 후속 후보입니다.

## 8. 화면 MVP 초안

메뉴 후보:

- `발견함`
- `링크 수집`
- `소재 링크`

Codex 추천 메뉴명:

- **발견함**

이유:

- 링크뿐 아니라 나중에 파일 메모, 출처 확인, 제작 후보 연결까지 담을 수 있습니다.
- "스크랩북"과 다르게 아직 검토 중인 앞단이라는 느낌이 있습니다.

첫 화면 구성 후보:

- 상단: 링크 추가 입력 영역
- 필터: 전체 / 받은 링크 / 확인 중 / 보관 / 제외 / 권리 확인 필요
- 리스트: 제목, 플랫폼, URL, 메모, 상태, 생성일
- 버튼: 열기, 복사, 상태 변경, 제작 후보로 표시, 메모 수정, 제외

준비중으로 남길 버튼:

- 로컬 파일 연결
- 메타데이터 가져오기
- AI 요약

## 9. 저장 위치 기준과 후속 후보

1차 MVP 저장 위치는 이미 결정되어 적용되었습니다. 아래 선택지는 후속 확장 때 다시 볼 기준입니다.

2026-07-03 현재 기준:

- 1차 MVP에서는 새 `discovery_links` Cosmos container를 바로 만들지 않습니다.
- 기존 Cloud DB 구조 안에서 `docType: discovery_link` 방식으로 작게 시작했습니다.
- 단, `/videos` 저장 영상 조회에 `docType: discovery_link` 문서가 섞이면 안 됩니다.
- 링크 수와 기능이 커지면 별도 `discovery_links` container 분리를 다시 검토합니다.

### 저장 후보 A: 새 `discovery_links` 저장소

장점:

- 의미가 가장 명확합니다.
- 스크랩북, videos, videoUserRecords와 섞이지 않습니다.
- 나중에 local assets, production candidates와 연결하기 좋습니다.

단점:

- 새 DB 저장소 또는 새 `docType` 설계가 필요합니다.
- 새 endpoint가 필요합니다.

### 저장 후보 B: 기존 `videos` container에 `docType: discovery_link`

장점:

- 기존 Cosmos container를 재사용할 수 있습니다.
- 새 container를 만들지 않아도 될 수 있습니다.

단점:

- `videos` container가 여러 문서 타입을 더 많이 품게 됩니다.
- 쿼리와 인덱스 설계가 지저분해질 수 있습니다.

### 저장 후보 C: 기존 scrapbook 확장

장점:

- 빠르게 시작할 수 있습니다.

단점:

- 스크랩북의 의미가 흐려집니다.
- "검토 전 발견함"과 "보관 완료 스크랩북"이 섞입니다.

### 저장 후보 D: localStorage만 사용

장점:

- 백엔드 없이 시작할 수 있습니다.

단점:

- 기준 데이터가 아닙니다.
- 브라우저 캐시 삭제 시 사라질 수 있습니다.
- 이미 정한 Cloud 우선 원칙과 맞지 않습니다.

Codex 추천:

- 현재 MVP에는 **저장 후보 B: 기존 `videos` container에 `docType: discovery_link`** 방식이 적용되어 있습니다.
- 다만 저장 영상 조회 `/videos`에 discovery link 문서가 섞이지 않는 API 경계가 반드시 필요합니다.
- localStorage만 사용하는 MVP는 추천하지 않습니다.
- scrapbook 확장은 빠르지만 장기 구조상 추천하지 않습니다.

## 12. 최종 판정

현재 단계에서는 discovery links 1차 MVP가 부분 구현되었습니다. 수동 링크 저장, 상태/권리 상태 관리, URL 복사, 제작 후보함 연결까지 1차 범위에서 동작합니다. local assets 기능은 아직 구현하지 않습니다.

1차 MVP 범위는 **수동 링크 저장 중심의 발견함**이 가장 안전합니다. 로컬 파일은 실제 파일을 다루지 않고, 필요하면 2차에서 "파일 메모 카드" 수준으로 검토합니다.

2026-07-03 배포 환경에서 읽기 전용 확인을 했습니다. `GET /discovery-links`는 성공했고 현재 Cloud 발견함 링크는 0개입니다. `GET /videos`는 `channelIds` 없이 호출하면 400으로 거절되어, 저장 영상 조회와 discovery link 조회가 API 경계상 분리되어 있음을 다시 확인했습니다.

2026-07-03 사용자 승인 후 발견 링크 저장/수정/삭제 smoke test를 완료했습니다. 임시 링크를 Cloud에 저장하고, `status: candidate`, `rightsStatus: needs_check`, 제목·메모 수정, 삭제를 확인했습니다. 최종 재조회에서 Cloud 발견함 링크 0개와 임시 smoke 링크 0개를 확인했습니다.

다음 확장으로 넘어가기 전에는 local assets, 별도 제작 프로젝트 모델, 별도 container 분리 여부를 작은 Issue로 나누어 확인해야 합니다.
