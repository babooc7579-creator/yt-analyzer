## 2. 현재 상태

현재 앱은 React + Vite 기반 프론트엔드입니다.

2026-07-18 기준으로 초기의 `App.jsx` 집중 구조는 상당 부분 해소되었고, 주요 데이터/상태 흐름에는 회귀 테스트 안전망이 추가되었습니다.

- `src/App.jsx`는 현재 13줄 수준의 얇은 연결 파일입니다.
- 앱의 주요 상태와 워크플로우는 `src/hooks`로 분리되어 있습니다.
- 화면은 `src/components`로 나뉘어 있습니다.
- 데이터/화면 props 계산은 `src/utils`로 많이 분리되어 있습니다.
- Cloud API 호출은 `src/services`에서 관리합니다.
- `src/hooks` 내부 사용자 안내/오류 문구는 `src/utils`와 `src/constants`로 분리되어, hook은 상태 흐름에 집중하는 구조입니다.
- `src/services`의 공통 Cloud/YouTube API fallback 문구는 이름 붙은 상수와 테스트로 보호합니다.

최근 안정화 기준:

- Cloud/localStorage 기준, 영상별 사용자 기록, 스크랩북, 발견함, 제작 후보함, 채널 액션, workflow 조립 흐름을 작은 hook/service/utils 단위 테스트로 보호하고 있습니다.
- 스크랩북, 참고 보관함, 필터 결과 없음 화면에는 다음 행동 버튼을 추가했습니다. 이 버튼들은 화면 이동 또는 필터 조건 초기화만 실행하며 Cloud 저장, DB 쓰기, YouTube API 호출은 직접 실행하지 않습니다.
- 레이더 완료 화면은 제작 후보함으로 이어지고, 스크랩북 영상 카드는 기존 Cloud 판단 기록 기준으로 제작 후보 표시를 할 수 있으며, 제작 후보함에는 저장 영상 탐색/발견함 정리 다음 행동 버튼이 있습니다.
- 제작 후보 영상 카드에는 원본 링크, 제목 초안, 제작 메모, 업로드 예정일 준비 여부가 표시됩니다. 이 표시는 저장이나 API 호출을 실행하지 않습니다.
- 제작 후보함 상단에는 권리 확인, 일정, 제작 중 후보, 영상 후보, 링크 후보 중 우선 확인할 항목을 표시합니다. 이 표시는 저장이나 API 호출을 실행하지 않습니다.
- 홈 지표에는 제작 후보, `오늘 집중`, 발견 링크 후보 숫자가 함께 표시됩니다. `오늘 집중`이 있으면 권리 경고 다음 우선순위로 후보함 바로가기를 안내합니다. 홈 표시와 이동만으로 저장이나 YouTube API 호출은 실행하지 않습니다.
- 레이더 판단/초기화/되돌리기와 스크랩북의 제작 후보 표시는 Cloud 저장 중 중복 클릭을 막고 진행 상태를 표시합니다. 저장 구조나 endpoint는 바꾸지 않았습니다.
- 발견함 상태/권리 필터에는 현재 선택 상태와 안전한 필터 초기화 동작이 추가됐습니다. 초기화는 화면 필터만 바꾸며 Cloud 데이터를 수정하지 않습니다.
- `터또터 탐색`은 저장 영상 중 6개월 이상·채널 평균 대비 1.5배 이상인 후보를 전용 화면에서 검색·필터·정렬합니다. 화면 진입과 조건 변경은 YouTube API를 호출하지 않습니다.
- `오늘 볼 채널`은 운영중 채널을 미수집, 등급, 마지막 수집일 순으로 보여줍니다. 채널 선택은 수집을 실행하지 않으며 저장 영상 조회와 새 영상 수집 화면 이동을 분리합니다.
- `키워드 탐색`은 현재 불러온 Cloud 저장 영상의 제목과 채널명을 검색하고, 자주 등장한 제목 단어를 추천합니다. 검색·필터·정렬은 YouTube API를 호출하지 않습니다.
- 키워드 탐색에 저장 영상이 없고 선택 채널도 없으면 `오늘 볼 채널`로 안내합니다. 채널 선택 뒤 사용자가 명시적으로 저장 영상을 불러오는 2단계 흐름이며, 화면 이동과 선택만으로 YouTube API를 호출하지 않습니다.
- `태그별 금고`는 기존 채널의 태그와 카테고리를 기준으로 채널을 고른 뒤, 명시적인 저장 영상 불러오기 동작으로 Cloud DB 영상을 조회합니다. 태그 선택만으로 YouTube API를 호출하지 않습니다.
- `업로드 캘린더`는 기존 Cloud 영상별 사용자 기록의 `targetPublishDate`를 읽어 제작 후보 일정을 월별로 표시합니다. 일정 카드의 `후보함에서 찾기`는 제작 후보함을 열고 해당 영상 ID로 한 건을 정확히 좁혀 보여주며 Cloud 데이터를 바꾸지 않습니다. 후보함에서 전체 작업 보기 또는 캘린더로 돌아가기를 선택할 수 있고, 상태 필터 결과가 비면 전체 상태로 안전하게 되돌릴 수 있습니다.
- 제작 후보함은 영상 제목·채널·제목 초안·메모 검색과 진행 단계 필터를 지원하고, 현재 카드의 제목·메모·일정·원본 URL을 `작업 묶음`으로 로컬 클립보드에 복사합니다. 다음 행동에서 업로드 캘린더를 바로 열 수 있습니다.
- 홈의 제작 후보 숫자는 제작 후보함의 제작 전 단계 묶음 기준과 일치합니다. 오늘 집중 후보도 포함하고, 제작 중·업로드 완료 항목은 별도 단계로 구분합니다.
- 모바일에서는 좌측 메뉴가 첫 화면 전체를 가리지 않도록 높이를 제한하고 내부 스크롤을 사용합니다. 발견함, 스크랩북, 제작 후보함의 좁은 화면 배치와 긴 제목 표시도 보강했습니다.
- 사이드바는 실제 사용 가능한 17개 메뉴를 기본 표시하고, 준비중 14개는 `향후 기능` 접이식 영역에 보존합니다. 오퍼레이션 관제의 중복 메뉴 3개는 `채널 운영실` 하나로 통합했고, 기존 바로가기 ID는 호환 경로로 유지합니다. 준비중 안내 화면과 제품 로드맵은 삭제하지 않았으며, 접기/펼치기는 API 호출이나 데이터 변경을 실행하지 않습니다.
- 채널 운영실은 `채널 관리 → 새 채널 등록 → 필요할 때 새 영상 수집` 단계를 한 화면에서 연결합니다. 채널 수, 선택 수, 수집 기록, 불러온 영상 수에 따라 현재 상태와 다음 추천 행동을 표시하며, 저장 영상 조회와 레이더 이동을 바로 이어줍니다. 단계 이동과 채널 선택만으로 Cloud 저장이나 YouTube API 호출은 실행하지 않습니다.
- 오늘의 레이더와 채널 운영실의 저장 영상 불러오기는 Cloud DB 조회 중 진행 상태를 표시하고 중복 클릭을 막습니다. 조회 실패 시 같은 화면에서 다시 시도할 수 있으며, 실패 안내는 이 동작이 YouTube API를 호출하지 않았음을 함께 표시합니다.
- 터또터 탐색, 키워드 탐색, 태그별 금고, 레이더 빈 화면의 저장 영상 불러오기도 같은 조회 진행 상태를 사용합니다. 조회 중에는 버튼을 비활성화하며 API endpoint나 조회 조건은 바꾸지 않습니다.
- 오늘의 레이더는 점수순 상위 6개만 화면에 표시하고, 한 건을 판단하면 다음 미판단 후보를 자동으로 보충합니다. 별도 다음 페이지 버튼은 없으며 화면 안내에 이 동작을 명시합니다.
- 최근 전체 검증 기준은 `npm test -- --run --reporter=dot`, `npm run build`, `git diff --check` 통과입니다. 2026-07-18 기준 테스트는 `213개 파일 / 916개 테스트`까지 통과했습니다. Cloud 작업 오류는 전역 안내로 표시되며, 로그인·권한·네트워크 계열 오류에서 Microsoft 로그인 경로를 바로 다시 열 수 있습니다. 입력 누락이나 중복 채널 같은 사용자 입력 안내에는 로그인 버튼을 표시하지 않습니다.
- 프로덕션 빌드는 React, Lucide 아이콘, 앱 코드를 별도 캐시 파일로 나눕니다. 앱 동작이나 화면 라우팅을 지연 로딩하지 않으며, 각 JS 묶음이 500 kB 아래라 기존 대형 chunk 경고는 해소됐습니다.
- 로컬 브라우저에서 실사용 메뉴를 데스크톱으로 열었고, 홈·키워드 탐색·태그별 금고·제작 후보함·업로드 캘린더·채널 운영실을 390px 모바일로 확인했습니다. 가로 넘침과 console error가 없으며, 이 점검에서는 저장·삭제·수집 버튼을 누르지 않았습니다.
- 운영 앱은 Azure Static Web Apps Standard와 Microsoft Entra 로그인을 사용합니다. 앱과 같은 도메인의 `/api`는 `creator_owner` 역할로 보호되며, Edge에서 owner 로그인과 저장 영상 조회가 확인됐습니다.
- 프론트엔드, Function App, Cosmos DB 등 운영 리소스와 백엔드 GitHub OIDC 배포 경로는 Microsoft Azure Sponsorship 구독으로 전환됐습니다. 이전 MCPP의 관리 ID와 빈 `yt-analyzer-rg`도 정리 완료했습니다.
- 제작 칸반은 1차 MVP에서 제작 후보/제작 중/업로드 완료 3개 칼럼을 유지합니다. 기존 장기 상태 후보는 저장값을 바꾸지 않고 제작 후보 칼럼에 표시해 화면 누락을 막습니다.
- 제작 후보의 `오늘 집중`은 기존 Cloud 판단 기록의 선택적 `focusPinnedAt`으로 보존합니다. 백엔드 PR #12와 프론트엔드 PR #885 배포는 성공했으며, owner 계정의 고정 후 새로고침 왕복 확인은 운영 점검으로 남아 있습니다.
- 제작 후보 저장 중에는 같은 영상의 집중/상태 요청을 중복 전송하지 않으며, 네트워크 예외가 나면 저장 중에 멈추지 않고 실패 상태로 돌아옵니다.
- 이 검증은 "버그가 절대 없다"는 의미가 아니라, 핵심 흐름을 고치다가 기존 동작이 깨지는 위험을 훨씬 빨리 발견할 수 있는 상태라는 뜻입니다.
- 홈 레이더 흐름, 홈 제작 후보/발견 링크 후보 지표, 발견함 빈 상태/필터/헤더 액션/오류 복구 안내, 스크랩북/참고 보관함, 제작 후보함 빈 상태/다음 행동과 저장 실패 안내, 제작 후보 카드 준비 체크, 제작 후보함 우선 확인 안내, 채널 안전 버튼, 영상 카드/리스트 액션, 댓글 Top 10 모달 상태 문구까지 렌더링 테스트로 보호합니다.

## 3. 주요 파일

```txt
README.md
```

프로젝트 소개, 실행 방법, 배포 안내가 정리되어 있습니다.

```txt
docs/APP_BLUEPRINT.md
```

앱의 큰 목적, 사용자 흐름, 화면 구성, UI/UX 방향이 정리되어 있습니다.

```txt
docs/ARCHITECTURE.md
```

앞으로 가져갈 전체 폴더 구조와 리팩터링 방향이 정리되어 있습니다.

```txt
docs/WORK_LOG.md
```

작업 히스토리와 커밋 기록을 남기는 문서입니다.

```txt
src/App.jsx
```

현재는 레이아웃과 라우트를 연결하는 얇은 파일입니다. 큰 변경 대상이 아니라, 관련 hook/component를 작게 정리하는 방식으로 유지합니다.

```txt
src/config.js
```

앱 전체 설정값을 분리하기 위해 새로 추가한 파일입니다.

```txt
src/hooks
```

앱 상태, 채널 워크플로우, 영상 워크플로우, 발견함, 스크랩북, 제작 후보 흐름이 분리되어 있습니다.

```txt
src/services
```

Cloud Function API와 localStorage 보조 저장 접근을 담당합니다.

```txt
docs/CREATOR_OS_DOCUMENT_INDEX.md
```

현재 Creator OS 문서를 어떤 순서로 읽어야 하는지 정리한 문서입니다. 코드 작업 전 먼저 확인합니다.

## 6. 앞으로의 리팩터링 순서

반드시 작은 단위로 진행합니다.

7. 전체 UI 대개편보다 현재 작동하는 흐름을 안정화한 뒤 화면 단위로 개선합니다.

## 7. 개발 시 절대 주의할 점

- 기존 핵심 기능을 한 번에 삭제하거나 갈아엎지 않는다.
- API Key를 저장소에 커밋하지 않는다.
- Azure Function API 주소는 설정 파일로 관리한다.
- YouTube API 호출과 Azure API 호출을 섞지 않는다.
- 화면 코드 안에 긴 프롬프트 텍스트를 계속 추가하지 않는다.
- localStorage 접근은 기준 저장소가 아니라 Cloud 실패 시 임시 fallback으로만 다루고, 관련 접근은 `services/storage.js`와 hook 흐름 안에서 관리한다.
- 큰 변경 전에는 문서와 작업 로그를 먼저 갱신한다.
- 에러가 발생하면 어떤 커밋부터 문제가 생겼는지 추적 가능해야 한다.

현재:

- 채널/영상 데이터: Azure Function + Cosmos DB
- 스크랩북: Cloud DB 기준. 백엔드에서는 `videos` container 안의 `docType: scrapbook` 문서로 저장
- 영상별 사용자 판단 기록: 기존 `status` 유지 + `statusIds` 복수 판단 보존
- 발견함 링크: 새 별도 container가 아니라 현재 MVP에서는 `docType: discovery_link` 방식
- localStorage: 기준 저장소가 아니라 Cloud 실패 시 임시 fallback과 기존 데이터 보호 용도
- 제작 후보: 현재 별도 `production_candidates` 저장소 없이 `videoUserRecords`와 발견 링크 `status: candidate`를 사용

장기 의사결정:

- 사용자 계정 기반 저장이 필요한지
- 스크랩북을 장기적으로 별도 container로 분리할지
- 발견 링크를 별도 container로 분리할지
- 제작 후보를 별도 production model로 분리할지
- local assets를 어떤 방식으로 저장/연결할지
- scan/api quota 로그를 어디에 저장할지

### 8.4 백엔드 저장소 역할

관련 저장소:

```txt
babooc7579-creator/yt-analyzer-functions
```

프론트엔드와 백엔드의 역할을 문서화할 필요가 있습니다.
