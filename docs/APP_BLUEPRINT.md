# 타임머신 CRM - 앱 설계도

> 이 문서는 `yt-analyzer` 앱의 제품 방향과 현재 구현 기준을 함께 정리한 설계 문서입니다.
> 목표는 단순한 유튜브 데이터 조회 도구가 아니라, **유튜브 소재를 발견하고, 판단하고, 보관하고, 제작 후보로 이어주는 개인용 Creator OS**를 만드는 것입니다.

---

## 1. 앱의 핵심 목적

타임머신 CRM은 유튜브 채널과 영상을 관리하면서, 과거에 터졌던 영상 소재를 다시 발굴하는 도구입니다.

핵심 컨셉은 다음과 같습니다.

- **모니터링**: 관심 있는 유튜브 채널을 언어/카테고리/태그별로 저장합니다.
- **수집**: 채널의 영상 데이터를 주기적으로 모읍니다.
- **발굴**: 조회수, 평균 대비 성과, 업로드 기간, 좋아요 비율 등을 기준으로 좋은 소재를 찾습니다.
- **해석**: 왜 터졌는지 후킹 포인트를 분석합니다.
- **전환**: 한국어 콘텐츠 제목, 쇼츠 대본, 리메이크 아이디어로 바꿉니다.
- **보관**: 좋은 영상과 아이디어를 스크랩북에 저장합니다.

---

## 2. 사용자의 기본 흐름

1. 홈/오늘 레이더에서 오늘 볼 후보와 현재 작업 상태를 확인
2. 관심 채널을 등록하고 태그/언어/등급/운영 상태를 정리
3. 필요할 때만 새 영상 수집 버튼으로 YouTube API 기반 수집 실행
4. 저장 영상 불러오기로 Cloud DB에 이미 저장된 영상을 조회
5. 필터와 정렬로 후보 영상 찾기
6. 또터또 후보를 보고 제작 후보, 나중에 보기, 제외 등으로 판단
7. 좋은 영상은 스크랩북/참고 보관함에 보관
8. 외부 URL은 발견함에 수동 저장하고 권리 상태와 후보 여부를 표시
9. 제작 후보함에서 영상 후보와 발견 링크 후보를 함께 확인
10. 원본 URL 또는 AI 리메이크 프롬프트를 복사해 실제 제작 도구로 이동

## 3. 현재 화면 구조

현재 UI는 "오늘 무엇을 볼지"에서 시작해 채널, 저장 영상, 발견함, 보관함, 제작 후보함으로 이어지는 구조입니다.

```txt
좌측 사이드바
├─ 오늘 레이더 / 홈
├─ 채널 목록 / 채널 등록
├─ 저장 영상
├─ 발견함 / 링크 수집
├─ 스크랩북 / 참고 보관함
├─ 제작 후보함
├─ 대본 보드
├─ 업로드 캘린더
└─ 준비중 메뉴

상단 헤더
├─ 현재 선택된 작업명
├─ Cloud/수집/저장 안내
└─ 빠른 실행 버튼

메인 영역
└─ 현재 메뉴별 핵심 작업 화면과 다음 행동 안내
```

## 4. 메뉴별 설계

### 4.1 오늘 레이더 / 홈

홈은 현재 앱의 상태를 한눈에 보여주고, 오늘 어떤 후보를 보면 되는지 안내하는 첫 화면입니다.

필수 카드:

- 등록 채널 수
- 수집된 영상 수
- 오늘 후보 / 처리 기록
- 제작 후보 수
- 발견 링크 후보 수
- 스크랩/참고 보관 상태
- 언어별/태그별 채널 분포

홈의 목적은 사용자가 앱에 들어오자마자 “오늘 무엇을 보면 되는지”, “이후 어디로 이어가면 되는지” 알게 하는 것입니다.

### 4.2 채널 관리

필수 기능:

- 단일 채널 추가
- 여러 채널 일괄 추가
- 채널 미리보기
- 태그 복수 선택
- 언어 선택
- 채널 메모 작성
- 채널 삭제
- 태그명 일괄 변경
- 태그별 채널 목록 보기

UX 원칙:

- 채널 추가는 “입력 → 미리보기 → 태그 선택 → 저장” 순서로 명확히 나눕니다.
- 일괄 추가는 별도 탭으로 분리해 실수를 줄입니다.
- 채널 카드는 구독자 수, 평균 조회수, 최근 스캔일, 등록 태그가 한눈에 보여야 합니다.

### 4.3 영상 발굴

필수 필터:

- 키워드 검색
- 조회수 기준
- 쇼츠/롱폼 구분
- 언어
- 태그
- 업로드 기간
- 정렬 기준: 조회수, 평균 대비 배수, 일 조회수, 좋아요 비율, 최신순

영상 카드에 보여야 할 정보:

- 썸네일
- 제목
- 채널명
- 업로드일
- 조회수
- 좋아요 비율
- 평균 대비 성과 배수
- 쇼츠/롱폼 표시
- 스크랩 버튼
- 댓글 분석 버튼
- AI 프롬프트용 체크박스

### 4.4 또터또 / 오늘 레이더

또터또 모드는 “터진 건 또 터진다”라는 앱의 핵심 철학을 담는 화면입니다.

기준:

- 업로드 후 6개월 이상 지난 영상
- 해당 채널 평균 대비 높은 성과
- 현재 한국어 콘텐츠로 리메이크 가능한 소재
- 댓글 반응이 강한 영상
- 제목 구조가 재활용 가능한 영상

화면 설계:

- 상단에 또터또 설명 카드 배치
- 후보 영상을 점수순으로 정렬
- 후보를 봤음, 나중에 보기, 제작 후보, 제외로 판단
- 완료 상태에서는 제작 후보함이나 저장 영상 탐색으로 이어지는 다음 행동 제공
- 여러 영상을 선택해 AI 리메이크 프롬프트 생성

### 4.5 스크랩북

스크랩북은 좋은 소재를 버리지 않고 쌓아두는 공간입니다.

필수 기능:

- 스크랩한 영상 목록
- 태그별 분류
- 메모 추가
- 리메이크 상태 표시: 미검토, 분석 완료, 대본화 완료, 제작 완료
- AI 프롬프트 복사
- 원본 영상 바로가기
- 제작 후보로 표시

### 4.6 발견함 / 링크 수집

발견함은 유튜브 앱 밖에서 발견한 인스타, 틱톡, 웹 링크 등을 수동으로 저장하는 공간입니다.

필수 기능:

- URL 수동 저장
- 제목/메모 저장
- 상태값: inbox / reviewing / saved / candidate / discarded
- 권리 상태: unknown / needs_check / cleared / do_not_use
- 제작 후보함으로 이어지는 후보 표시
- 외부 사이트 자동 수집이나 자동 다운로드를 하지 않는다는 안내

### 4.7 제작 후보함

제작 후보함은 저장 영상 후보와 발견 링크 후보를 한곳에서 확인하는 작업 화면입니다.

현재 기준:

- 별도 `production_candidates` 저장소는 없습니다.
- 영상 후보는 `videoUserRecords`의 상태 기록을 사용합니다.
- 발견 링크 후보는 발견함의 `status: candidate`를 사용합니다.
- 원본 링크, 제목 초안, 제작 메모, 업로드 예정일 준비 여부를 표시합니다.
- 권리 확인, 지난 일정, 일정 없는 제작 중 후보, 링크 후보 같은 우선 확인 항목을 표시합니다.

### 4.8 대본 보드 / 업로드 캘린더

대본 보드는 제작 후보함의 영상 작업을 글쓰기 중심으로 정리하는 전용 화면입니다.

현재 기준:

- 별도 대본 container나 새 endpoint를 만들지 않습니다.
- 기존 Cloud `videoUserRecords`의 `draftTitle`, `note`, `targetPublishDate`를 그대로 사용합니다.
- `note`는 현재 MVP에서 인트로, 구성, 대본 초안을 함께 적는 제작 메모입니다.
- 제작 후보함, 대본 보드, 업로드 캘린더는 같은 Cloud 제작 기록을 서로 다른 작업 관점으로 보여줍니다.
- 입력은 명시적 Cloud 저장 버튼을 눌러야 반영되며, 화면 진입과 필터 변경은 YouTube API를 호출하지 않습니다.
- 미저장 입력이 있으면 사이드바, 인접 제작 화면 이동, 브라우저 새로고침 전에 이탈 경고를 표시합니다.

장기적으로 구조화된 전체 대본 모델이 필요해지면 별도 데이터 결정으로 검토하며, 현재 MVP에서는 스키마를 확장하지 않습니다.

### 4.9 설정 / 준비중 메뉴

설정 화면에는 사용자가 헷갈릴 수 있는 기술 요소를 모읍니다. 2026-07-15 기준 1차 설정 화면이 실사용 메뉴로 연결됐으며, 기존 채널 분야 관리와 현재 데이터/API 기준을 한곳에서 안내합니다.

현재 연결 항목:

- 채널 분야 추가, 화면에서 숨김, Cloud 태그 이름 변경
- 숨긴 기본 분야와 Cloud 태그를 브라우저 화면 목록에 다시 표시
- Azure Function API Base URL 확인
- 데이터 저장 위치 안내
- 저장 영상 조회와 YouTube API 수집 작업 구분
- 댓글 Top 10용 사용자 YouTube API Key 입력 상태 확인
- Cloud 판단 기록/스크랩북 동기화 경고와 현재 화면 오류 확인
- Cloud 채널 목록 수동 재조회와 오류 유형별 다음 행동 안내
- GitHub Actions 배포 상태 확인 경로

후속 항목:

- CORS 원인 자동 판별
- 로컬 실행 안내
- Azure 리소스 상태를 앱 안에서 자동 진단하는 기능

준비중 메뉴는 실제 기능처럼 보이면 안 됩니다. 클릭 시 API 호출이나 DB 변경 없이 안내 화면만 보여야 합니다.

## 5. UI 톤앤매너

앱은 전문가용 분석 도구이지만, 사용자는 개발자가 아닐 수 있습니다. 따라서 UI는 다음 원칙을 따릅니다.

- 어려운 개발 용어보다 작업 중심 문구를 사용합니다.
- 버튼 이름은 명확하게 씁니다.
- “분석”, “스캔”, “발굴”, “스크랩”, “리메이크” 같은 행동 단어를 중심으로 구성합니다.
- 숫자는 한국식 축약 표기를 사용합니다. 예: 25000 → 2.5만
- 오류 메시지는 원인과 다음 행동을 함께 안내합니다.

## 6. 현재 개발 우선순위

### Phase 1. 구조 안정화

- 완료된 상태입니다.
- `App.jsx`는 얇은 연결 파일로 정리됐습니다.
- 주요 상태 흐름은 `src/hooks`, 화면은 `src/components`, 계산/문구 props는 `src/utils`, API 호출은 `src/services`로 분리됐습니다.
- 핵심 흐름은 테스트로 보호합니다.

### Phase 2. 화면 흐름 안정화

- 진행 중입니다.
- 버튼 문구에서 Cloud DB 조회, Cloud 저장, YouTube API 호출, 로컬 클립보드 복사를 구분합니다.
- 빈 화면, 오류 화면, 완료 화면에는 다음 행동을 제공합니다.
- 홈, 발견함, 스크랩북, 제작 후보함 사이의 이동 흐름을 작게 다듬습니다.

### Phase 3. 분석 기능 강화

- 또터또 점수화
- 영상별 후킹 포인트 메모
- 댓글 반응 요약
- AI 리메이크 프롬프트 템플릿 고도화

### Phase 4. 크리에이터 OS 확장

- 발견 링크와 로컬 파일 연결
- 별도 제작 프로젝트 모델
- 업로드 후보 관리 / 제작 칸반 확장
- 한국어 제목 변환 히스토리
- 채널별 벤치마킹 리포트

주의: Phase 3~4 중 DB schema, endpoint, localStorage key, YouTube API 호출량이 바뀌는 작업은 별도 선택지 보고 후 진행합니다.

## 7. 좋은 첫 화면의 기준

앱을 켰을 때 사용자가 바로 이해해야 할 질문은 다음 3가지입니다.

1. 지금 내가 등록한 채널은 몇 개인가?
2. 오늘 새로 볼 만한 영상은 무엇인가?
3. 리메이크할 만한 또터또 후보는 무엇인가?

첫 화면은 이 3가지 질문에 답해야 합니다.

## 8. 개발 시 주의사항

- 기존 기능을 한 번에 갈아엎지 않습니다.
- 먼저 문서화하고, 그다음 화면을 나눕니다.
- API 연동부와 UI 표시부를 분리합니다.
- 저장소에 민감한 API Key를 커밋하지 않습니다.
- 사용자가 직접 실행하기 쉽도록 README를 계속 갱신합니다.

## 9. 현재 코드에서 확인된 주요 특징

현재 앱은 이미 다음 기능을 포함하고 있습니다.

- React/Vite 기반 프론트엔드
- TailwindCSS 스타일 구조
- Azure Function API 연동
- 채널 목록 클라우드 로딩
- 채널 단일/일괄 추가
- 태그/언어 관리
- 채널 스캔 요청
- 수집된 영상 조회
- 오늘 레이더 후보 표시와 판단 기록 저장
- 쇼츠/롱폼 필터
- 조회수/성과배수/일조회수/좋아요 비율 정렬
- 댓글 Top 10 조회
- 스크랩북 Cloud 우선 저장
- 발견 링크 수동 저장과 제작 후보 표시
- 제작 후보함에서 영상 후보와 발견 링크 후보를 함께 확인
- 제작 후보 카드의 작업 준비 체크
- 제작 후보함의 우선 확인 안내
- AI 리메이크 프롬프트 복사
- 주요 화면 흐름과 문구를 보호하는 테스트

참고: 현재 스크랩북은 Cloud DB 기준이며, localStorage는 Cloud 연결 실패 시 임시 fallback과 기존 데이터 보호 용도로만 봅니다.
참고: 현재 발견 링크는 별도 `discovery_links` container가 아니라 Cloud DB의 `docType: discovery_link` 방식으로 관리하며, 제작 후보함에는 별도 제작 DB가 아니라 발견함 상태값 기반 후보로 표시합니다.
참고: 현재 제작 후보는 별도 `production_candidates` 저장소가 아니라 영상 판단 기록과 발견함 상태값을 이용합니다.

따라서 앞으로의 방향은 “처음부터 다시 만들기”가 아니라, **현재 기능을 잘 보존하면서 구조와 사용성을 정리하는 것**입니다.
